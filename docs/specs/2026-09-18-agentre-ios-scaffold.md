# agentre-ios：原生 iOS 对话端

> Status: Draft
> Owner: agentre 维护者
> Last updated: 2026-09-29

**Objective:** 让用户在 iPhone 上看到自己账号下所有机器正在跑的 agent 会话，并能就地推进一轮——发消息、批准或拒绝工具权限、回答 agent 的提问。

**Hard invariant:** `agentre-server` 不因本轮产生任何行为变更；iOS 端以现有 `mobile` 设备种类接入既有中继链路，不新增、不修改任何服务端端点、表或协议消息。`agentre` 仓仅新增 Swift 生成产物与其构建声明，Go 与 TypeScript 两侧的既有产物逐字节不变。

## Problem

1. **手机上够不着「等你批准」。** 服务端把「需要关注」建模为会话索引上的 SQL 判据（`internal/repository/agent_session_repo/summary.go:150` 的 `attentionExpr`），控制台据此渲染角标；但推进一轮所需的动作——发消息、答权限、答提问——**全部只存在于中继 RPC 上**，REST 面（`internal/api/agentsession/session.go` 的 list / read / transcript / attention-count）是只读的。结论：现有网页控制台在手机上能看见 agent 卡住，却无法解除它。**已核实。**

2. **网页端为浏览器限制付的代价，原生端不必付。** 浏览器原生 WebSocket 设不了请求头，所以控制台要先换一张两分钟有效的 relay ticket，再把它伪装成 `agentre.bearer.<token>` 子协议偷渡进 `Authorization`（`internal/api/router.go:375-377` 与 `frontend/src/lib/relayUrl.ts` 记录了这条绕行及其理由）。原生端可直接设头，这一整套绕行连同票据续期都不需要。**已核实。**

3. **服务端已经为 `mobile` 留了门，但没有人走过。** `/v1/oauth/device/authorize` 的 `device_kind` 绑定标签是 `oneof=desktop agentred mobile`（`internal/api/device/device.go:7`），而 `device_entity` 只定义了 `desktop`/`agentred`/`web` 三个常量，`kind` 列按自由字符串原样落库、无常量校验。**已核实。**

## Actors and user stories

1. 作为**已有 agentre 账号的开发者**，我想在离开电脑时从 iPhone 看到哪些会话在等我，以便不必回到电脑前就解除阻塞。
2. 作为**同一个开发者**，我想在手机上读完 agent 给出的命令与理由后直接批准或拒绝，以便一轮能继续跑下去。
3. 作为**同一个开发者**，我想在手机上补一句指令或回答 agent 的提问，以便修正方向而不必等到回到电脑前。

## Design decisions

| # | 决策 | 依据与被否方案 |
|---|---|---|
| 1 | iOS 端只经 `agentre-server` 中继接入，不做局域网直连 agentred | 中继是唯一外网可达且已有完整 RPC 面的通道。被否：局域网直连——需要自签证书固定、设备发现与 `auth.direct` 凭据三套新逻辑；且 agentred 只对 `desktop` 种类的凭据下发直连凭据与地址（`agentre/docs/architecture.md` 的远程执行一节），`mobile` 本就拿不到 |
| 2 | 以 `mobile` 设备种类走 RFC 8628 设备流取得设备 access token，并以该令牌直接连 `/v1/relay/client` | `/v1/relay/client` 的 client 侧同时接受原生端设备 access token 与浏览器票据；`isAddressableKind()`（只认 desktop/agentred）仅约束 `/v1/relay/daemon`，client 侧无种类门。被否：复用网页的 relay ticket——那是为浏览器设头限制而生的两分钟短票，原生端用它只会白白引入续期逻辑 |
| 3 | 逐通道握手的凭据即设备 access token，由 agentred 回调服务端 `/v1/credentials/introspect` 核验 | 该端点走 `auth_svc.BearerResolver`，不区分种类；设备凭据的 `PeerFingerprint` 即该设备自身指纹（`internal/service/device_svc/bearer.go:68`）。被否：为移动端新增一类凭据——服务端会因此产生变更，违反本轮不变式 |
| 4 | `wire.proto` 的 Swift 产物由 `agentre` 仓生成并持有，本仓以 **git submodule** 钉不可变 revision、SPM 以本地路径依赖消费 | 与工作区既有不变式同形：`agentre/` 拥有产物，消费方钉已推送的不可变 revision。钉法用 submodule 而非 SPM 的 `url:revision:`，因为后者**只认仓库根目录的清单**——实测以 revision 拉 `agentre` 仓得到 `error: the package manifest at '/Package.swift' cannot be accessed`，而 Swift 产物的清单在 `pkg/wire/swift/`；Go 原生支持嵌套 module（`pkg/wire` 自带 `go.mod`），Swift 不支持。被否：把清单移到 `agentre` 仓根目录——桌面端仓根多出一份 Swift 清单，且每次构建 iOS 都要让 SwiftPM 克隆整个桌面仓。协议兼容判据是版本号逐字相等（当前 **`0.2.0`**，见 `agentre/pkg/wire/proto/agentre/wire/wire.proto:46`；版本取自该文件选项而非任何一侧的字面量），钉不准即握手被拒。被否：本仓自带一份 `.proto` 自行生成——同一 schema 出现第二个主人，与既有的「全工作区只有一份 `wire.pb.go`」守卫精神相悖 |
| 5 | 移动端自有一套设计语言，不复用 `@agentre-hub/agentre-ui` 的视觉；**这套语言就是 `agentre-mobile.pen`，稿子是视觉契约** | 该包是 React 实现，Swift 侧无法消费；且手机的信息密度、触达区与主导作业（审批）与桌面/控制台不同。被否：照搬控制台配色与密度——会得到一个被压窄的网页而不是一个 iOS 应用。**2026-09-29 修订（用户决定）**：原先稿子只作佐证、视觉交给实现者用系统默认样式自拟，结果十四屏无一与稿子一致（配色另起一套、tab 栏在二级页不收、导航与组件形态全是系统默认，见运行验证后的对照审计）。被否：只改全局（色值、字体、tab 栏）不动各屏——各屏的组件形态与信息层级才是稿子的主体 |
| 6 | 主色取稿子的钢蓝 `primary`，「运行中」交给绿色 | 蓝色接管「可交互」与品牌后，若再兼表「运行中」则同一颜色承担两种语义。原先写的「沿用桌面端品牌蓝」由实现者落成了一枚与稿子不同的亮蓝；2026-09-29 起以稿子的取值为准。被否：以电光青柠同时表主操作与运行中——性格鲜明但与既有品牌脱节，且语义重载 |
| 7 | 深色与浅色两套主题都做，随系统切换 | iOS 用户期待跟随系统。代价是每个色值出两套并各自过对比度 |
| 8 | **手机自有一套会话记录，摘要与转录都落本地库** | 手机是第三个宿主，与桌面端、与 `agentre-server` 的会话镜像并列，不是某一份远端列表的取景器。本地库带来的是：冷启动直接出内容、断网与飞行模式下历史照常可读、滚动翻历史不发网络请求。它不构成第二个真相源——**机器始终是权威**，本地库只按 `seq` 游标做增量追加，重连后补齐，冲突时以机器为准。形状上与服务端的 `mirror_svc` 完全同构（认领机器 → `attach` → `pull` → 落自己的库），那已是工作区里验证过的做法。被否：不落库、每次冷启动重拉——手机的网络与电量条件不同于常驻的桌面端，且离线时整个应用无内容可读 |
| 9 | 本轮不含推送通知 | 推送需要服务端新增令牌登记、APNs 客户端与镜像写入路径上的跃迁检测，落在 `agentre-server` 仓，与本轮不变式冲突。它作为独立一轮交付，依赖顺序在本轮之后 |
| 10 | 整体按即时通讯隐喻组织，而非运维控制台 | 服务端已把会话建模成 IM（未读判据、已读回执端点、消息行加帧号账本、按游标的离线拉取）；按 IM 组织时屏上每个元素都指得回一个既有字段。被否：分区式控制台列表（等你处理／运行中／最近）——紧迫性最清楚，但与后端结构不同构，且每个分区都要用户先学会它是什么 |
| 11 | 权限审批用内联卡片，不升起模态 | 与 IM 的消息流一致，多条待处理可各自独立存在，不必排队弹窗。被否：一律底部 sheet——其唯一站得住的优势是承载卡片放不下的长输入，而那可以由卡片摘要加展开解决 |
| 12 | 界面不写解释性文案 | 状态用可供性表达即可；解释性文字会随实现漂移成谎言，且在小屏上挤占本就稀缺的高度。被否：在计数、环形、继承分组旁各配一句说明——那正是本轮清理掉的东西 |
| 13 | 不做任何危险操作启发式 | 协议只带工具名与原始输入，判定危险只能靠客户端字符串匹配：漏判给虚假安全感，误判让用户开始无视警示。被否：本地正则标红；被否：让 agentred 算出后果并扩协议——那要改协议与两个既有宿主，撞本轮不变式 |
| 14 | **会话数据一律经中继取自机器，本轮不调用服务端的任何会话端点** | 服务端的会话镜像是为网页控制台而设的一份记录，范围是账号的「保存名单」（`agentre-server/internal/model/entity/agent_session_entity/save.go:11`：「没保存过的对话一个字都不落库」，守卫 `internal/api/savedsession/guard_test.go:33`）。手机既然自有一套记录（决策 8），再去读那一份就是同时维护两份、且两份的集合不同，用户无从知道自己在看哪一个。中继侧的取材是齐的：`sessionList`（关键词 / `limit` / `cursor` / 按 `conversation_ids` 收窄，新到旧）、`sessionCounts`（总数 / 运行中 / 等你处理）、`attach` + `pull`（带 `oldest_seq` 与 `has_more`，历史可反向翻）——`agentre/pkg/wire/proto/agentre/wire/wire.proto:500,537,615,627`。因此 `/v1/agent-sessions/*` 与 `/v1/saved-sessions` 在本轮一次都不调；REST 只承担登录、工作区（Agent／派发目标／项目树）、设备与账号 |
| 15 | **机器详情页就是发现与保存的入口**，并区分已保存与未保存 | 本地库要有东西进来，就必须有一个地方让用户指着说「这条我要」。那个地方只能是机器详情——它本来就是「这台机器上有什么」的那一屏。两种状态必须在同一行上分得开，否则用户无法判断某条会话是已经在手机上了还是只是在机器上看得见。被否：另开一个「导入」屏——同一份列表拆成两处，用户要在两屏之间比对才知道自己收了哪些 |
| 16 | **本地库只收两类：手机上新建的，与用户主动从机器保存的** | 与服务端镜像同一条规矩——范围由用户显式给出。自动把每台在线机器的全部会话都收进来，会在手机上堆积从不查看的会话，且每一条都要拉全量转录，流量与存储都不可控。被否：自动全收；被否：只收手机新建的——那样你在电脑上开的会话手机永远推不动，而审批恰恰是本轮的主导作业 |
| 18 | 本地库用 SwiftData，除非首个落地任务证明它扛不住帧追加 | 随系统走、无第三方依赖、与 `@Observable` 同源，符合本轮「用最新技术栈」的取向。逃生口写在这里而不是留给实现者临场决定：帧是**按 `seq` 追加且需去重**的写入，若该任务的红灯测试显示批量追加的代价不可接受，改用直接的 SQLite（`sqlite3` 或 GRDB）并在计划的 note 里记下实测数字。无论哪种，库的接口由领域层声明，表现层看不见实现 |
| 17 | 未读与已读位由本地库自己记 | 服务端的已读回执端点只对它自己那份镜像有意义，而本轮不碰那一份。未读判据因此落在本地：会话的最后活动时刻晚于本机记录的已读位即为未读，从未读过的判为未读 |
| 19 | **稿子与本规格冲突时：视觉按稿，行为按规格**（用户决定，2026-09-29） | 外观、排版、颜色、字体、组件形态照稿子；凡是影响「屏上所说是否属实」的地方——离线机器的计数、未读的形态、未保存会话的保存入口、排队消息何时发出、不可用原因的措辞、没有来源的耗时——保留本规格的语义，用稿子的视觉呈现。被否：一律按稿子——稿子是示意数据，照搬会让若干处显示编出来的数 |
| 20 | **稿子上没有数据来源的元素不做**，也不放占位（用户决定，2026-09-29） | 逐项倒推后有十项找不到来源，列在 Out of scope。本轮不改服务端与 agentred（Hard invariant），这些元素要么需要它们改动，要么根本没定义做什么。被否：在手机上用已有数据拼凑——例如机器详情只在已翻到的那一页里筛「运行中」，看起来像全量筛选实则不是；被否：连服务端一起补——打破本轮不变式 |
| 21 | **项目与 Agent 头像用宿主同一套 16 色身份色**，不用稿子示意的 5 色（用户决定，2026-09-29） | 服务端为每个项目存了 `color`、为每个 Agent 存了 `avatar_color`（`agentre-server/internal/api/workspace/workspace.go:35-36,170-171`），取值是宿主的 `agent-1…agent-16`（`agentre-ui/src/lib/agent-color.ts:10-45`）。同色才能让同一个项目在桌面、控制台、手机上一眼认出。被否：按稿子 5 色折算——同一项目在手机上与桌面异色 |
| 22 | **「退出登录」先在服务端撤销本机，再清本地**（用户决定，2026-09-29） | 原先退出只清本地，服务端仍把这台 iPhone 记为已授权设备；稿子把设备列表收进二级页、「我」页底部只留一个「退出登录」。撤销本机与退出登录因此合成同一个动作。被否：只清本地——留下一台用户以为已经退掉的授权设备 |
| 23 | **底部 tab 栏按稿子自绘**，只在三个顶层页出现（用户决定，2026-09-29） | 稿子是浮动的圆角栏、线性图标、选中项浅色胶囊；系统 TabView 在 iOS 26 是 Liquid Glass 形态，与稿子不同，且二级页不收起。被否：系统 TabView 加 token 着色——形态仍与稿子不同 |

## 形态与边界

本仓 `agentre-ios` 是工作区中与 `agentre`、`agentre-server`、`agentre-hub` 并列的第四个独立 git 仓库，独立提交。它对 `agentre` 仓有且只有一条依赖：以 git submodule（`Vendor/agentre`）钉一个已推送的不可变 revision，SPM 以本地路径 `Vendor/agentre/pkg/wire/swift` 依赖其中的 `AgentreWire`（生成类型前缀 `Agentre_Wire_`）。submodule 取 `origin`（GitHub）的地址——跨仓钉位一律走 GitHub，与 `agentre-server` 钉 Go module 同一条路。升级协议就是把 submodule 挪到一个新的已推送 revision，那一次提交只含这一处 gitlink 变化。

代码主体位于本仓的本地 Swift 包中，应用目标只作为组装层存在。模块之间的依赖方向单向向下，且该方向由包清单结构性强制——声明外的模块无法被 import，不依赖评审或文本扫描守卫：

- 领域层持有模型、可观察状态与仓储**协议**，不依赖任何传输实现；
- REST、中继与本地持久化三个模块各自实现领域层声明的协议——持久化与传输同级，都是领域层声明、外层实现；
- 表现层只依赖领域层；
- 应用目标是唯一知道全部具体实现的地方，负责装配。

跨仓交付按依赖顺序发生：先在 `agentre` 仓落地并推送 Swift 产物及其构建声明，本仓再钉该 revision。**在不可变 revision 可用之前，本仓不得先行写入任何依赖它的代码。**

## 连接与协议

一个账号在任一时刻只持有一条物理 WebSocket 连接，其上多路复用若干虚拟通道；这与控制台的连接模型一致，不因移动端打折。

- **通道寻址**有且只有两种形式：按对话寻址（服务端解析出承载该对话的机器）与按机器寻址（调用方已选定机器，或对话尚不存在）。前者用于打开一条已存在的会话，后者用于机器作用域的操作与新建对话。**手机上的会话通道一律按机器寻址**：服务端只对账号保存名单里的对话解析 `conversation:` 目标，未保存的对话明确归机器那一轴（`agentre-server/internal/service/relay_svc/target.go:8-12`），而手机不读也不写那份名单（决策 14）。本地库因此为每条会话记下承载它的机器指纹，打开、补齐、回应审批都经那台机器的 `machine:` 通道，RPC 以 `conversation_id` 参数指明是哪一条。
- **握手逐通道进行**：一条连接上的两条通道可能接向两台不同机器，各自须向其对端出示凭据。凭据即本设备的 access token。
- **协议版本判据是逐字相等**，没有区间可谈。握手因版本不等被拒时，应用**停止对该通道重试**，并以「这个版本的 App 连不上你的服务端，请更新 App」告知用户；不得把协议错误码或英文原串呈现给用户，也不得表现为一个转不完的等待。
- **断线补齐**：连接恢复后，对用户正在关注的对话重做握手、重新 attach，再按 `seq` 游标拉回缺失区间；拉回的帧与实时帧经同一条投递路径处理，`seq` 不大于游标者即为重复，只应用一次。

payload 的编解码使用由同一份 schema 生成的 Swift 消息类型，帧的封装形式（中继信封与 RPC 分帧）与既有两侧实现保持同一格式和同一套校验。

## 登录

用户在登录屏看到当前服务器地址与一个主操作。触发后应用以 `mobile` 种类发起设备流，并**直接打开服务端返回的带确认码的验证地址**——用户不需要手动输入确认码。授权完成后应用取得 access token 与 refresh token。

- 设备指纹是一枚在本设备首次生成、此后持久保存的随机值，**不使用系统提供的厂商标识**：后者在重装后改变，而这枚指纹既是逐通道握手出示的身份，也是此前从本机发起的对话上留着的来源标注——它一变，那些对话就认不回是自己发起的了。
- 令牌与设备指纹保存在系统钥匙串，仅本设备可用、不随账号同步到其它设备。
- 访问令牌过期时以刷新令牌换新并重试原请求；同一时刻只进行一次刷新。刷新被拒即视为登出，返回登录屏。
- 服务器地址可改，默认指向生产地址。

## 界面与交互

界面稿见维护者本机的 `agentre-mobile.pen`（十四屏：消息、对话及其上下文浮层与步骤展开两态、审批、更多面板、新建对话及其按项目挑选、草稿派单与选执行机器、机器详情、登录、机器、我；每屏另有一份浅色实例，与深色屏是同一份内容的主题实例而非副本）。**稿子是视觉契约**（决策 5，2026-09-29 修订）：每一屏的布局、密度、层级、组件形态、颜色、字体、图标与文案以稿子为准，稿子里的示意数据不是契约——屏上呈现的是真实数据。稿子与以下文字冲突时，视觉按稿、行为按规格（决策 19）；稿子上没有数据来源的元素不出现（决策 20，逐项列在 Out of scope）。逐屏的对照要求见下文「逐屏视觉契约」。

**整体隐喻是即时通讯，而非运维控制台。** 这不是风格偏好：协议本身就是这么建模的——会话的最后活动时刻配上本机已读位就是未读，`waiting_for_input` 就是「对面在等你回」，转录的消息行加帧号账本就是消息表加消息序号，`attach` 加按 `seq` 游标 `pull` 就是离线消息拉取，而本地库就是那份聊天记录。界面按 IM 组织时，屏上每个元素都能指回一个既有字段；按控制台组织时则不能。

**界面不写解释性文案。** 状态由可供性本身表达——一个正在跳动的点、一个填了四成的环、一条置顶并抬高的行，都不需要旁边再跟一句话说明它是什么意思。禁止出现的包括：解释某个数字怎么算出来的、预告点下去会发生什么、复述标题已经说过的事。界面呈现事实与操作；机制写在文档里，不写在屏幕上。本轮自己踩了三次，留作判据：选机器面板下写「只影响这一次」（预告点下去会发生什么）、草稿屏中央写「和某 Agent 开始对话」（导航栏已经说了是谁）、机器详情页的列表上方写「这台机器上的会话」（那一整屏都是这台机器）。判法是同一个：把这句话删掉，用户少知道什么事实？答不上来就删。

**设计语言。** 凡机器产出的内容——命令、路径、机器名、指纹、版本号、后端种类——以等宽字体 **JetBrains Mono** 呈现；人类可读文本以无衬线字体 **Inter** 呈现（两者都随 App 打包，不依赖系统字体；中文字形由系统回退补齐）。这一对比本身承担区分职责，不额外加框；稿子个别处把机器名排成正文字体、把人话提问排成等宽，以本条为准。颜色只表状态不作装饰：蓝表可交互与品牌，绿表运行中，琥珀表等你处理，红表失败——**唯一的例外是项目与 Agent 的身份色**（决策 21），它只出现在头像字形上。不可用的原因（离线、未配对、未配置路径）用次级文字色而不是红色：不可用不是失败。**界面中不得出现硬编码色值**，一切颜色取自具名 token，且每个 token 同时具备深浅两套取值。**引用一个不存在的 token 必须是构建期错误**：它的失败形态不是报错而是静默降级成某个兜底色，在深色界面上几乎看不出来。

**token 的取值就是稿子的变量**：`bg`、`surface`、`surface-2`、`line`、`line-strong`、`ink`、`ink-2`、`ink-3`、`idle`、`primary`、`primary-ink`、`primary-dim`、`run`、`run-dim`、`amber`、`amber-dim`、`coral`、`coral-dim`、`ctx-ok`、`ctx-warn`、`ctx-danger`、`glass`、`scrim`、`shadow`、`shadow-soft`，深浅两套逐一照抄稿子（`glass`、`scrim`、`shadow*` 带透明度）。稿子的 `proj-1…5` 与 `on-proj` 不用，改用宿主的身份色 `agent-1…agent-16` 与 `agent-neutral`，深浅两套取自 `agentre/frontend/packages/agentre-ui/styles/tokens.css:172-191,358-376`，字色一律白色。**只有六处为过对比度线偏离稿子**，偏离量不超过每通道 9/255：深色 `ink-3` `#7B8291`→`#808796`、`primary-dim` `#1A2738`→`#162334`；浅色 `ink-3` `#6B707A`→`#626771`、`amber` `#8F5D08`→`#8E5C07`、`ctx-warn` `#8F5D08`→`#8E5C07`（稿子里它与 `amber` 本就同色）、`run` `#0B7A55`→`#067550`。原因是稿子在 `surface-2` 上放次级文字（搜索框占位）、在 `primary-dim` 上放选中 tab 的文字、上下文百分比随环的档位着色，原值分别只有 3.94–4.46 的对比度。`idle` 只画状态点，按指示色的 3.0 线算。

**机器详情是发现入口：它列的是那台机器上的会话，现问机器要。** 与消息列表读本地库不同，这一屏读的是 `sessionList` 的实时答复，按游标分页、不一次取全。**每一行须分得清它是否已经在手机上**：已保存的行给出进入对话的去处，未保存的行给出「保存到手机」。保存即认领——立刻 `attach` 并按游标 `pull` 把这条会话的转录拉进本地库，此后它出现在消息列表里，与手机自己新建的那些没有区别。

**保存需要那台机器在线**，因为拉取要它来答。机器离线时这一屏没有会话可列，界面呈现的是「这台机器不在线」与它最后在线的时刻；**已经保存过的会话不受影响**，它们在消息列表里照常可读，只是推不动。

**机器详情顶部的三个计数取自那台机器现算的会话计数**（`sessionCounts`：总数、运行中、等你处理）。**机器离线时这三个数一个都没有**：界面呈现「不在线」这个事实，不显示为零——零是一个断言，而此刻我们什么都不知道。

**按机器浏览支持按标题搜索**，关键词直接交给机器（`sessionList.keyword`）。协议写明标题的大小写不敏感子串匹配是保底，宿主可另行匹配它自己拥有的分组名，而 agentred 只存同步标识、没有名字可匹配（wire.proto:501-505）。界面因此**只承诺匹配会话标题**：机器名、Agent 名、项目名都不保证参与。界面的提示文案须把这一点说出来，否则用户输入 Agent 名搜不到会判定功能坏了，而实际上是搜错了维度。切换筛选或改变搜索词时分页游标回到起点——范围变了还接着上一页的位置翻，翻的是另一个集合里的位置。

**打开一条会话时连哪台机器由本地库那一行给出**，不必让服务端再解析一次：保存这条会话时它来自哪台机器，就记在哪台机器上。本地库另记一个发起端指纹，那是来源标注而非连接目标，二者不可互相代替。

**消息列表**是应用主屏，**读的是本地库**：冷启动直接出内容，断网时照常可读，翻历史不发请求。连接建立后，已保存的会话各自 `attach` 并按游标补齐，新到的帧落库并就地反映到列表上。默认按最后活动时间倒序；等你处理的会话置顶并抬高视觉权重，且**在不进入对话的前提下即可读到待批准的具体命令或待回答的问题**。运行中的会话，其预览行呈现为「正在输入…」——这不是比喻，它与 IM 的同名状态是同一件事：对端正在产生内容，你在等。未读以行尾一枚圆点表达（不写条数），判据是会话最后活动时刻晚于本机已读位。

**这份列表的范围就是本地库的范围**（决策 16）：手机上新建的，以及你在机器详情页主动保存过来的。它不随任何远端列表变化——机器上新开了一条会话，不会自己出现在这里；要收就去机器详情页收。

**对话**中，用户消息为右侧气泡，agent 回复为全宽无气泡、带头像与署名——因为 agent 一侧要承载代码与命令输出，气泡会破坏其可读性。

**一轮里的工具调用可能有几十次，转录必须承受得住。** 这套规则既有宿主已经定型，**本轮照搬而不是另立一套**——否则同一份转录在两端读起来是两回事。

- 一段连续活动合并为**一个块**：一行组头加一条可展开的步骤时间轴。组头依次是展开指示、活动图标、步数、分类汇总、耗时。
- 分类汇总按**固定顺序**输出：思考、查阅、改 N 个文件、写入、命令、其它、N 失败。改文件那一档额外报出规模（改到几个文件、增删多少行）。
- **失败计数与后台运行计数单列在末尾，永不参与截断。** 一轮里唯一需要人过问的往往就是失败那一步，把它折进省略里等于藏起来。
- **失败的判据不止一个布尔。** 命令类工具会把退出码写在结果里，只认结果上的错误标志会把一条退出非零的命令判成成功。折叠态的计数与展开后的标记必须用同一个判据，否则会出现「组头说零失败、展开是几行红的」。
- **耗时只在一轮落定后显示，运行中留空**：耗时没有块级来源，运行中填一个数就是在编。
- **运行中的块自动展开**，落定后自动收起；用户主动点开时要的是全貌，不再省略。
- 运行中超过阈值步数即省略，只保留末尾若干行，被省略的部分收成一行，其上带着被省略部分的汇总与失败数。这条只在运行态生效。
- 运行中的组头**不放当前步的实时尾巴**。既有宿主在组头那一格滚动显示正在跑的那一步，那格在手机宽度上放不下一条命令，截断到只剩几个字后它既读不出是什么、又把失败计数挤出屏幕。运行态的组头只留脉冲点与「执行中 · N 步」，当前这一步由块内自动展开的末行呈现——它本来就在下面一行。
- **Subagent 折叠态只占一行**：一枚展开指示、`Subagent · <名称>`、以及右端的步数与耗时。它是嵌套的另一个执行体，值得一个卡片壳把它与正文分开，但那个壳在手机宽度上只该有一行高——把工具分类汇总也塞进去会让它比它所嵌套的那段正文还显眼。汇总在展开后由它自己的活动块给出。界面用词一律是 **Subagent**，与既有宿主的 zh-CN 文案一致，不另造「子任务」。
- **活动块不套容器**：组头与步骤行都没有边框、底色或圆角，展开后的步骤只靠一条左侧竖线归组。它是这条消息正文里的一段，不是消息旁边的一个对象；给它一个卡片壳会让它与真正的卡片（审批、Subagent）同级，而那两者才是需要单独处理的东西。
- **视觉权重按工具落的档决定，而档不查工具名表。** 判据依次是后端算好的规范类型、输入的形状、都不匹配则落中性档。认不出来的工具**不假装它是只读**——给它只读档的轻量呈现是在误导。
- **审批、提问、计划审批、Subagent 派生这四类不进活动块**，它们在既有宿主里就是被过滤出去的一档，各自是独立卡片。Subagent 尤其不能摊平进上层步数：那会把「5 步」写成「23 步」，而其中 18 步属于另一个执行体。
- 内容持续追加时，**用户向上滚动后即停止自动跟随**；此时出现回到最新的入口并标明其间新增了多少。

对话**不得相对既有宿主丢失对话态能力**。输入区下方常驻一行：展开面板的入口，以及权限模式、模型、思考档位三项各一枚图标；该行右端是上下文用量。三项以图标呈现而不带文字，它们各自的当前取值由展开面板逐行标注——常驻行负责「点得到」，面板负责「说得清」。

展开面板提供：权限模式、模型、思考档位、会话信息、上下文、删除会话。

**权限模式随每一轮发送带过去，而不是靠一次「立即切换」。** 宿主就是这么做的：控制台每一轮 `runtime.run` 都带上当前生效的档位（`agentre-server/frontend/src/components/session/useSessionSend.ts:301`），桌面端先落库、再尽力下发给活着的 CLI、CLI 不在时不报错（`agentre/frontend/src/components/agentre/permission-mode/use-permission-mode.ts`）。`runtime.setPermissionMode` 只对正在跑的这一轮有意义——一轮结束后 agentred 已把会话收掉，它一律回「没有进行中的一轮」（`agentre/internal/daemon/handlers/runtime.go:1454-1462`、`:1682-1689`）。因此：两轮之间切档只改本机记下的当前档，不报失败；一轮正在跑时再额外调 `runtime.setPermissionMode` 让它即刻生效，那一次失败才如实呈现。起手档位的取法与控制台同：用户这次选的 → 转录里执行端报过的当前档 → 执行端报的默认档。

**每一轮被接受后，手机再补发一次 `runtime.setPermissionMode`（当前档）。** 运行验证实测（report-11，用户决定）：`runtime.run` 带上的档位只在 agentred 为这一轮新起 claude 进程时生效；上一轮的进程还在池里（闲置 15 分钟内）时它被原样复用，新档不下发（`agentre/internal/pkg/agentruntime/runtimes/claudecode/runtime.go:620-626`，复用判据 `launchIdentity` `:725-733` 不含档位），于是两轮之间切到 plan 后，接下来两轮实际仍按旧档运行，界面却显示新档。一轮已被接受时这一轮已在 agentred 登记、进程在池中，`runtime.setPermissionMode` 能落到活着的 CLI 上（`claudecode/runtime.go:342-357`）。所以：手机发出的每一轮——包括排队消息取回合并后发出的那一轮——在 `runtime.run` 被接受后立即补发一次当前档，**不论这次是否切过档**（App 重启、别的客户端改过档之后也一并纠正）。补发晚于这一轮的用户消息交给 CLI：两轮之间切档后，下一轮从补发落地起按新档检查工具调用、这一轮开头的推理可能尚未看到新档，再下一轮完全按新档运行。补发失败（这一轮已经结束、执行端不支持权限模式等）不提示、不改变这次发送的结果。应答丢失、靠查询确认已被接受的那一轮不补发，下一轮照常补发。被否方案：只在切过档后的下一轮补发——本机标记在 App 重启后丢失、别的客户端改档无从得知，复用进程时仍按旧档跑；等 agentred 修复复用逻辑——不在本仓库，且桌面端与控制台经 agentred 远程对话时同样受影响，记为 agentre 仓库的后续事项。

斜杠命令与提及不占面板条目：它们由用户在输入框中直接键入触发，并就地给出候选。斜杠命令的候选按当前会话的工作目录作用域解析。

停止本轮与排队并存：一轮运行中输入框不被禁用，新消息进入队列，界面如实告知它们何时发出。语义照搬宿主而非另立：排着的是**插话**，由运行中的这一轮消费；本轮正常结束时仍未消费的那几条经 `runtimeDrainPending` 取回、以空行相连合成一条再发出（`agentre-ui/src/composer/steer-queue.ts`），宿主文案「AI 完成后插入」（`zh-CN/chat.json:284`）。规格原先写的「本轮结束后依次发出」与宿主不符，已更正。

上下文用量以环形加百分比呈现——只画一个没有标注的环，第一次见到的人读不出它是什么。环按用量分三档变色（正常／告警／危急），这是它相对线性条的主要价值：外围余光就能察觉快满了。点击弹出一枚锚在环上的浮层，只给已用与上限的绝对值。

**该浮层只读，不承载任何动作入口**，也不解释上限从哪来。既有宿主的同名组件早已是这个决定，本轮沿用而不是重新讨论。

上下文用量在上下文窗口取值不为正时**整块不渲染**，而不是渲染成零。

**新建对话选的是 Agent，不是机器。** Agent 持有一条带次序的执行目标链，落到哪台机器由该链解析得出；界面呈现解析结果（「当前落到某机器」），不可用时呈现具体原因并压暗该行。入口屏提供搜索、最近用过的若干个，以及全部 Agent。

**项目是新建对话里的第二条路，不是一组静态标题。** 入口屏另有一个「从项目里挑」的去处，进入后先选项目、再在该项目下选 Agent。项目是一棵树，所以该屏须同时呈现**直接加入本项目的 Agent** 与**从父项目继承下来的 Agent**，并把两者分开标注（继承的一侧按祖先由近到远各成一组、组名写出祖先项目名）——继承是这个模型里真实存在的一档，合并呈现会让用户以为某个 Agent 直接属于当前项目。两组互斥：既是直接成员又是祖先成员时只算直接，同一个 Agent 不在同一屏出现两次。

**继承关系在客户端计算。** 服务端只如实回答「这个 Agent 直接加入了哪些项目」并下发整棵项目树；把同一条规则在服务端再实现一遍，两处分叉后就没人说得清哪个对。祖先链的遍历须能容忍成环——树由桌面端建立，环不该出现，但真出现时要的是「列不全」而不是卡死。

**选完 Agent 先落到草稿态，派单在那里定。** 选 Agent 那屏每行尾部那句「当前落到某机器」是**解析结果**，不是选择器；把覆盖入口塞进列表行，等于要求用户在还没决定用哪个 Agent 之前先改它的执行目标。选中之后进入的是一条尚未发出第一条消息的对话：转录区为空，输入区上方常驻一行两枚 chip——机器与项目，各自点开一个底部面板。发出第一条消息后这一行退场。

**机器是覆盖，不是自由选择。** 可选范围就是该 Agent 的执行目标链，面板逐档列出次序号、机器名、后端种类；不可用的档**列出但压暗并写明原因**（离线 / 未配对 / 这台机器上未配置远端路径），而不是从列表里抹掉——用户需要知道那台机器在链上、只是此刻用不了。默认是自动按次序解析；用户手动指定后，面板底部出现交回自动挑的入口。**覆盖只对这一次生效**，不改 Agent 的配置。

面板标题与三种不可用原因的措辞取自既有宿主，不自创。**但不写「只影响这一次」这类预告**——覆盖不落到 Agent 配置是行为约束，写在这里；屏幕上由「交回自动挑」这个入口的存在本身表达。

**发出第一条消息的同时，这条对话进本地库。** 对话由手机自己铸号、派发到机器上跑，落库与派发是同一件事的两半：派发成功而没落库，用户退回消息列表会看不见自己刚发起的那条，从而再建一条。派发成功后落库失败时，界面须如实说明这条对话**已经在机器上跑起来了**、只是没能加进列表，并给出重试；不得假装成功，也不得呈现为没建起来。

**项目决定工作目录，因而决定跑不跑得起来。** 项目在目标机器上的路径不存在时，该 Agent 在这一屏不可用，界面须给出这一具体原因，而不是笼统的「不可用」。

**权限审批为转录流中的内联卡片**，不升起模态。卡片须呈现：请求种类、完整命令或输入（等宽、单独成块）、执行目录，以及**三档并列的处置**——「拒绝」「本会话始终允许」「仅本次允许」。这三档与文案都取自既有宿主，**不自创档位也不自创措辞**：审批是要用户承担后果的动作，两个宿主上同一句话必须指同一件事。**唯一的例外是英文的中间一档**：宿主原文「Always Allow This Session」与另两枚在手机宽度上排不进一行（运行验证实测三枚竖排、卡片约占屏高三分之一），手机端英文改用「Allow for Session」——所指不变，只是更短；中文照用宿主原文。三者按承诺范围从左到右排列，视觉分量依次是描边、浅底、主色实心，承诺越大的越不像顺手一点的东西。输入过长时卡片呈现摘要并提供展开。agent 提问（AskUserQuestion）复用同一卡片形态。

**卡片里不再套盒子，也不再加色带。** 命令块只用一层浅底把机器文本与人类文本分开，不再额外描边——外层卡片已经有一圈边框，内层再描一圈就是同一句话说两遍，而移动端卡片只有 331pt 宽，每一层边框都在吃可读宽度。标题行同理直接排在卡片里，不铺整条底色：卡片边框、盾牌图标、标题文字已经是三处同色标记，第四处只是在和用户真正要读的那条命令抢注意力。

**执行目录与命令合成一块，按终端的样子排**：目录在上、`$` 与命令在下，共用同一层浅底。它们都是机器文本、都是等宽，拆成两个元素只是让卡片多一条缝；合成一块之后它的形状本身就在说「这是一个 shell 会执行的东西」，不需要文件夹图标来解释目录是目录。

**处置按钮不配图标，也不做通栏。** 三个标签本身没有歧义，图标只是把按钮内容撑宽；给「拒绝」配一个红色叉号更糟——它把三档里最安全的那个染成了危险色，真正需要犹豫的是允许。通栏同理：两枚 44pt 高的通栏按钮把一张审批卡撑到接近屏高的四分之一，而按标签宽度排、右对齐一行就够——右对齐还顺带让最常用的那档落在拇指弧内。中英文两种语言下都必须是一行。

**可点区域一律补满 44×44pt，与绘制尺寸无关。** 设计稿里工具条上的图标按钮绘制成 36×36、筛选芯片 24pt 高、审批卡片上的三枚处置按钮 34pt 高——这些都是刻意的视觉分量，不是可点区域。实现须把每个可点元素的命中区扩到 44×44 且**互不重叠**；审批卡片上相邻两枚按钮之间尤其要留出明确的死区——「本会话始终允许」紧挨着「仅本次允许」，两者命中区一旦相接，误触代价最高的那一档就成了最容易点到的那一档。

**界面不得自行判定某次工具调用「危险」。** 协议只携带工具名与原始输入，不携带后果信息；基于字符串匹配的危险启发式会同时产生漏判（给出虚假安全感）与误判（使用户开始无视警示）。界面如实呈现工具名与输入，由用户判断。

**无障碍与本地化。** 全部界面文本进入字符串目录，提供简体中文与英文两种语言，且不得以拼接方式构造句子。界面支持系统字号放大；状态不得仅以颜色区分，须同时有文字或图标。

**导航**为三个顶层目的地：消息、机器、我。「我」包含账号信息、服务器地址、已授权设备列表与撤销、语言、外观与退出登录。**撤销只对本机生效**：服务端只允许一台设备用自己的令牌撤销它自己（`agentre-server/internal/controller/device_ctr/device.go:164-167`，目标不是调用者即 403），而改服务端违反本轮不变式。其它设备照常列出，在那一行写明到网页控制台撤销——这是一个用户否则无从知道的事实，不属于解释性文案。

**退出登录就是撤销本机**（决策 22）：先请服务端撤销本设备，再作废本地令牌、断开连接、清空本地库、回到登录屏。服务端撤销失败（离线、服务端不可达）时照样完成本地这一半，不把用户困在已登录状态。设备列表里本机那一行的「撤销」与「退出登录」是同一个动作。

### 逐屏视觉契约

以下每条都以稿子的对应屏（深色与浅色两份实例）为对照；未列出的视觉细节同样以稿子为准。

**全局框架。**
- **底部 tab 栏只在三个顶层页出现**（消息、机器、我）：稿子的浮动圆角栏，`glass` 底，三项线性图标加文字，选中项为 `primary-dim` 胶囊、图标与文字 `primary`。其余一切页面——对话、草稿、新建对话流程、机器详情、「我」的二级页——**不显示 tab 栏**，键盘弹起时它也不从键盘后面透出。
- 顶层页标题是左对齐的大字（「消息」「机器」「账号」），右上动作是行内图标，不用系统大标题的收缩行为和圆形玻璃按钮。
- 二级页导航栏是稿子的紧凑一行：左侧 `primary` 色返回箭头，中间标题区，右侧动作。系统的边缘右滑返回照常可用。
- 底部面板高度贴合内容，不留大片空白；行排在 `bg` 底的分组圆角卡片里，每行左侧一枚线性图标、右侧取值与展开指示。
- **头像字形**：会话与项目用项目的身份色加项目名首字（原样大小写，宿主 `initialOf`），不属于任何项目的会话用中性字形；Agent 用它自己的身份色加宿主的 Agent 首字母规则（两个拉丁词取两个首字母大写，否则取首字大写）。身份色缺失或不在 `agent-1…agent-16` 之内时用 `agent-neutral`。会话挂着项目、而项目列表还没取到（例如离线冷启动）时，画一枚不带字的空白字形，不画中性字形——中性字形的意思是「不属于任何项目」，此刻我们并不知道。

**01 消息。**
- 头部是「消息」与右上的新建入口。
- 其下是搜索框「搜索会话、项目、机器」：在本地库里按会话标题、所属项目名、承载机器名做大小写不敏感的子串匹配，即输即筛，不发网络请求；清空后恢复全表。
- 列表是平铺行加分隔线，不做卡片。
- 每行左侧是会话的项目字形头像，头像右下角挂状态点：琥珀表等你处理，绿表运行中，其余不挂。
- 等你处理的行置顶、铺 `surface` 底，副行是琥珀色的待处理事项（命令等宽），行尾的琥珀计数是这条会话里尚未处理的请求条数。
- 运行中的行副行为绿色「正在输入…」。
- 未读的行标题加粗，行尾是一枚 `primary` 圆点，不写数字（决策 19：未读是有无，不是条数）。

**02 对话（含 02B 上下文浮层、02C 步骤展开、03 审批）。**
- **导航栏**：返回、项目字形头像、会话标题（单行截断）、副标题，右侧 ⓘ 打开会话信息。副标题按状态取值：运行中为绿色「正在输入…」，等你处理为琥珀色「等你回复」，其余为承载机器名（等宽、次级色）。
- **日期胶囊**（`surface` 底）：每个自然日的第一条消息前插一枚，写「今天 9:32」「昨天 9:32」或日期加时刻。时刻取帧的源端时刻，实时帧取本机收到的时刻。
- **用户消息**是 `primary` 底、`primary-ink` 字的右侧气泡。
- **Agent 回复**：左侧 `surface-2` 圆形头像内一枚 `primary` 图标；署名是后端的显示名（宿主 `shortLabel`，如「Claude Code」「Codex」），后接等宽的模型名。模型名取这一轮收场时执行端报的模型，运行中取会话当前的模型，都没有则不写。
- **活动块照稿子排版**：
  - 组头耗时写成「分:秒」。
  - 每步结果按工具种类写：搜索类「N 处」，读文件「N 行」，改文件「+N」，失败写「失败」（`coral`）。
  - 没有结构化结果的不写；**运行中的步骤不写耗时**（本节前文与决策 19）。
- **Subagent** 是 `surface` 底的单行卡片。
- **审批卡**：`amber` 描边，盾牌图标加标题。标题按请求种类写：命令类为「请求执行命令」，其余为「请求使用」加等宽工具名。三枚处置按本节前文。
- **输入区**：
  - 排队条（`surface` 圆角）写条数与「AI 完成后插入」（决策 19：保留何时发出）。
  - 输入框占位「接着说…」。
  - 右侧在运行中是停止钮（`surface-2` 底、`coral` 方块），否则是发送钮（`primary` 底，输入为空时压暗）。
  - 下方工具行依次是「+」（展开面板）、盾牌（权限模式）、芯片（模型）、大脑（思考档位），右端是上下文环加百分比，环按 `ctx-ok` / `ctx-warn` / `ctx-danger` 三档着色。
- **回到最新**的入口是 `glass` 底胶囊，写「N 条新内容」。

**04 更多面板。**
- 两组卡片：权限模式、模型、思考档位一组；会话信息、上下文、删除会话一组（删除为 `coral`）。
- 取值一律以人话呈现，不显示原串：
  - 权限模式：默认 / 接受编辑 / 计划模式 / 跳过权限确认。
  - 思考档位：低 / 中 / 高，以及执行端报出的更高档。
  - 执行端报出本表以外的值时，才原样等宽显示。
- 模型只写模型名（等宽），不带供应商前缀。
- 会话信息写承载机器名。
- 上下文写「已用k/上限k」（等宽）；上下文窗口不为正时这一格不写值。
- 行名用「思考档位」。

**05 新建对话 · 选 Agent。**
- 以模态呈现：左上「取消」，标题「新建对话」。
- 其下依次是：搜索框「搜索 Agent」；「从项目里挑」卡片，写项目个数；「最近用过」与「全部 Agent」两组，组标题是小号等宽字。
- 每行：Agent 头像、名称、副行「当前落到 <机器名>」。
- 不可用的行整行压暗，副行改写具体原因（次级文字色）。

**05B 从项目里挑。**
- 在模态内推入，返回写「新建对话」。
- 顶部是横向滚动的项目胶囊，子项目写成「父 › 子」，选中项为 `primary` 实心。
- 下面是「直接成员」一组，再按祖先由近到远各一组「继承自 <祖先项目名>」（互斥与去重规则见上文）。
- 每行：Agent 头像、名称、副行「当前落到 <机器名> · <路径>」（路径等宽），取这个项目下的派发结果。
- 不可用的原因措辞取自宿主（决策 19）。

**05C 草稿派单、05D 选执行机器。**
- 草稿导航栏：返回、Agent 头像、标题「新对话」、副标题 Agent 名。
- 输入区上方的两枚 chip（`surface` 圆角描边）：
  - 机器 chip：在线时绿色的机器图标、机器名、等宽后端种类、下拉指示。
  - 项目 chip：文件夹图标、项目名或「不指定项目」、下拉指示。
- 输入框占位「说点什么，开始这次对话…」，发送钮 `primary`，工具行同对话屏，没有上下文环。
- **草稿的工具行是可用的**（用户决定，2026-09-29）：在这里选的权限模式、模型、思考档位随第一条消息的 `runtime.run` 一起带过去，候选按机器 chip 当前选中的那台机器与后端取；一项都不选时按 Agent 与后端的既有配置运行（与此前行为相同）。改选机器后，已选的三项回到「不指定」——候选随机器变了。Pi 后端不提供权限模式这一项：它的 `permission_mode` 字段在派发时承载归属令牌（`Sources/AgentreRelay/Adapters/RelayDispatcher.swift:48-53`）。
- 发出第一条消息后，模态收起，这条对话在消息页的栈上打开；从对话返回回到消息列表。
- 选机器面板标题「在哪台机器上跑」，分组卡片逐档列出：等宽次序号、机器名、等宽后端种类，选中的打勾。不可用的压暗并写原因；手动指定后底部出现「交回自动挑」。

**06 机器详情。**
- 导航栏：返回、等宽机器名、等宽副标题「平台 · 种类 版本」（按上报原样，缺哪项不写哪项）。
- 在线时是三格计数卡：会话总数、运行中（`run`）、等你处理（`amber`）。离线时不出现三格，改为「这台机器不在线」与最后在线时刻（见上文）。
- 搜索框「搜索会话标题」。
- 每行：状态点、标题、等宽工作目录、相对时间。
- 行尾按是否已在手机上区分：已保存的是进入对话的展开指示，未保存的是「保存到手机」。
- 列表底部是「再加载 N 条」，N 取机器报的总数减去已列出的条数，以一页为上限；没有更多时不出现。

**07 登录。**
- 左上是 `primary` 等宽字标「AGENTRE」，其下是大字标语「在这台 iPhone 上接管你的会话」。
- 底部是服务器行（地球图标、等宽主机名，点开可改）与主按钮「用浏览器授权」（外链图标）。

**08 机器。**
- 标题「机器」，副标题「N 台已配对 · M 台在线」。
- 每台一张 `surface` 卡：状态点、等宽机器名、展开指示；等宽的「平台 · 种类 版本」一行（按上报原样：桌面端报系统与架构，agentred 只报系统）。
- 卡片分隔线下：
  - 在线：「N 个会话」（`run`）与「N 运行中 · N 等你处理」，取该机现算的会话计数，为零的项不写。
  - 离线：整卡压暗，只写最后在线时刻，**不写任何会话数**（决策 19）。

**09 我。**
- 页标题「账号」，tab 仍叫「我」。
- 账号卡：首字头像（`primary-dim` 底、`primary` 字）、显示名，副行为邮箱。
- 分组行：
  - 服务器（等宽主机名）：进入服务器地址编辑。
  - 已授权设备（条数）：进入设备列表二级页。
  - 语言、外观：各自进入选择页。
  - 关于：等宽版本号，不可点。
- 底部是 `coral` 描边的「退出登录」。

## 失败与恢复

| 情形 | 应用行为 |
|---|---|
| 应用进入后台被系统挂起，连接断开 | 这是移动端相对网页的新增失败路径。回到前台后重连、重做逐通道握手、重新 attach 并按游标补齐。用户看到的是内容续上，而非一条报错 |
| 网络在 Wi-Fi 与蜂窝之间切换 | 同上；重拨采用指数退让、封顶并带抖动 |
| 访问令牌过期 | 单次刷新后重试；刷新被拒则回到登录屏 |
| 协议版本不等 | 停止重试该通道，提示更新 App |
| 完全离线（飞行模式 / 无网） | 本地库照常可读：消息列表、已保存会话的完整历史都在。可发的动作不可用，界面如实说明是离线，不呈现为加载失败 |
| 一条已保存会话所在的机器离线 | 该会话仍可读到保存时为止的全部内容，只是推不动；不从列表里消失，也不呈现为空 |
| 账号下没有在线机器 | 如实呈现「没有可用的机器」及其原因，不呈现无限等待 |
| 一次 RPC 迟迟不返回 | 有兜底期限，到期后如实收场，不留下永久等待的界面 |

任何对用户可见的失败提示，均须由应用把机器产出的错误解析为事实后以用户语言重述，并据此决定是否给出下一步出口；不得直接呈现错误码或对端原始字符串。

## 兼容性与隐私

- **按最新工具链构建，不为旧系统留退路**：以本机的 Xcode 27 / iOS 27 SDK 构建（自 2026-04-28 起上传 App Store Connect 的包必须以不低于 iOS 26 的 SDK 构建，该下限自动满足），Swift 6.4、语言模式 6、严格并发全开，界面全部 SwiftUI 与 `@Observable`。**部署目标 iOS 26.0**——原先写的 18.0 是为多覆盖一代设备，但本轮的装机范围就是维护者自己的手机，多覆盖的那几代无人使用，而抬高下限换来的是源码中不出现任何 `if #available` 分支、新 API 直接用。若维护者的设备已在 iOS 27，下限可再抬一档；这一条由第一个建起工程的任务按实机系统版本确认后落定。
- 令牌、设备指纹与任何账号凭据只存于钥匙串，不写入日志、不写入崩溃报告、不随诊断信息上报。
- **应用在本地留存已保存会话的摘要与转录**（决策 8）。该库只存在于本设备，不随账号同步、不上传、不进入备份以外的任何通路；它与凭据分开存放——凭据在钥匙串，会话库是应用沙盒内的数据库文件，受系统的文件保护约束。
- **退出登录即清空本地库**，连同已读位与游标：换账号后不得看到上一个账号的任何会话内容。删除一条会话时本地那一份当场就没了。
- 与开发环境联调时需要的明文 HTTP 与本地网络访问例外，只存在于调试构建配置中，发布构建不得携带。

## Out of scope

- **推送通知（APNs）**——独立一轮，依赖顺序在本轮之后，含 `agentre-server` 侧的推送令牌登记、APNs 发送与「需要关注」跃迁检测。本轮范围内，用户只在应用处于前台且连接建立时看到待处理项。
- **局域网直连 agentred**——见决策 1。
- **项目与组织管理、引擎与模型的账号级配置、技能目录、端口转发、会话导入**——这些是控制台与桌面端的机器作用域操作，不属于「在手机上推进一轮」。手机上可切换**当前会话**用哪个模型与思考档位，但不能增删账号级的提供方与后端。
- **从某条消息分叉（fork）、MCP 服务器开关、插件开关、协作模式**——这四项是发起一轮时的配置态而非对话态，手机端沿用 Agent 与后端的既有配置，不提供入口。
- **图片附件**——既有宿主支持随消息附图，本轮手机端不提供入口。这是一处**已知的能力缺口**而非疏漏，记在此处以便后续一轮补上。
- **危险操作提示**——需要 agentred 计算后果并扩展协议，见决策 13。记为后续一轮的候选。
- **与网页控制台共享已读或保存名单**——两边各记各的（决策 14／17）。手机保存一条会话不会让它出现在控制台里，反之亦然。
- **把本地库的内容导出或备份到别处**——它只活在这台设备上。
- **iPad 与 macOS 适配**——本轮只针对 iPhone 形态。
- **稿子上没有数据来源的十个元素**（决策 20）：
  - 消息页：未读条数的数字；筛选按钮（没有定义筛什么）。
  - 机器页：右上「+」（配对发生在机器上，手机没有可调的端点）；agentred 机器的 CPU 架构（它只上报系统名）；离线机器的会话数（它此刻答不了）。
  - 机器详情：「运行中」「未读」筛选（`sessionList` 不按状态筛，未保存的会话没有已读位）；右上「⋯」菜单（没有定义做什么）。
  - 对话：步骤结果里「12 passed」一类的测试摘要（工具结果只有原文，没有结构化字段）；运行中步骤的耗时。
  - 草稿：从主列表选 Agent 后预选一个项目（没有取默认项目的规则）。

  需要它们时，先在服务端或 agentred 补上来源，另开一轮。
- **服务端为移动端补 `KindMobile` 常量或调整按种类分支的行为**——`workspace_svc` 中若干处按 `desktop`/`agentred` 分支（派发目标、项目位置、执行目标）在 `mobile` 设备出现后的取舍，属于服务端的判断，本轮只如实记录该集成点的存在。

## Testing decisions

| 接缝 | 验证什么 | 现有对照 |
|---|---|---|
| wire 消息编解码 | Swift 侧与 Go 侧对同一批帧同解同编：Go 产出一批**二进制金向量**与各自的期望字段值，Swift 解码后字段逐一相等；Swift 再编码回去，Go 解得到与原消息相等的消息。**判据不是字节逐一相等**——protobuf 不保证跨实现的字节级一致（map 序、未知字段的位置），把那个当判据会得到一条随实现升级而红的测试 | 本轮新建。**既有的 `agentre-wire/fixtures/` 那 23 份 JSON 不能用作本接缝的判据**：它们与 `src/codec.gen.ts` 由同一个 Go 生成器产出（`golden_test.go` / `tsgen_test.go`），是那层**手写 JSON 领域 codec** 的金样本，而那层是 TS 宿主为自己的 UI 而设的一层，iOS 直接消费 protobuf 结构、根本不经过它。实测 `protojson` 往返只有 5/23 结构相同，差异来自 64 位整数的字符串化、`DurableNotification` 的形状不同、`json.RawMessage` 透传字段，以及两份专门证明未知字段往返不丢的样本——最后一类 protobuf 消息永远做不到 |

| 本地化 | 字符串目录中不存在缺失语言的条目；界面不通过拼接构造句子 | 无 |

| 伪对端与真实对端同形 | 伪中继照搬已核实的 agentred 行为，而不是「什么都接」：一轮结束后 `runtime.setPermissionMode` 回「没有进行中的一轮」；`runtime.run` 带上的权限档位被记下可查；同一会话的执行进程还在时，`runtime.run` 带来的新档不改变实际生效的档位，只有这一轮进行中的 `runtime.setPermissionMode` 才改变它（`agentre/internal/pkg/agentruntime/runtimes/claudecode/runtime.go:620-626`）。凡是伪对端行为与真实对端不同的地方，都是一条会被盖住的缺陷 | `agentre/internal/daemon/handlers/runtime.go` |
| 主线界面流程（XCUITest，对本地伪服务端） | 仓库内一个 UI 测试 target 驱动真实构建的 App：测试进程在本机起一个伪 HTTP 服务端与伪中继，App 经启动参数指向它；走登录（设备流）→ 机器 → 保存到手机 → 新建对话并发出 → 审批 → 切权限模式 → 挂起回前台后打开着的对话屏续上 → 撤销本机回到登录屏。整条流程在**简体中文 × 英文、浅色 × 深色**四种组合下各跑一遍，并在稿子的十四屏各自对应的状态下留截图，供运行验证与稿子逐屏对照。确定、无需网络与账号，可重复跑 | 运行验证时 scratch 内的手写驱动（本 target 取代它） |

**与稿子的逐屏对照**由运行验证完成：在四种组合下把 App 各屏与稿子对应屏并排比对，逐屏给出是否一致。像素级自动比对不做——稿子用的是示意数据，App 显示的是真实数据。

无法自动化、需以真机运行观察确认的部分：权限审批卡片右对齐的三枚处置按钮是否真的落在拇指可达区，且相邻两枚不会误触；系统字号放大到较大档位时各屏是否仍可用。这两项在本轮收尾时以真机操作记录结论。挂起后回到前台的续上改由主线界面流程覆盖，真实服务端上的那一侧仍在运行验证里观察。
